SQL Transactions

Transactions group SQL statements into a single unit so the database stays correct even if something fails.

Why Transactions Exist

Without transactions, partial changes can leave your data inconsistent. Transactions ensure either everything succeeds, or nothing changes.

Basic Flow

BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

Rollback

If something goes wrong, rollback returns the database to its previous state.

BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
ROLLBACK;

Savepoints

Savepoints allow partial rollback inside a transaction.

BEGIN TRANSACTION;
UPDATE inventory SET qty = qty - 1 WHERE product_id = 5;
SAVEPOINT before_discount;
UPDATE order_summary SET discount = 20 WHERE order_id = 10;
ROLLBACK TO before_discount;
COMMIT;

ACID Properties

  • Atomicity — all statements succeed or none do.
  • Consistency — the database moves from one valid state to another.
  • Isolation — transactions do not interfere with each other.
  • Durability — committed changes persist even after a crash.

Isolation Levels

  • Read Uncommitted — may see uncommitted changes.
  • Read Committed — sees only committed data.
  • Repeatable Read — same query returns same rows in one transaction.
  • Serializable — behaves as if transactions run one at a time.
